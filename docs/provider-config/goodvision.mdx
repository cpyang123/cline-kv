---
title: "GoodVision SmartRouter"
description: "Run Cline through GoodVision's OpenAI-compatible SmartRouter gateway, with policy-driven model routing."
---

GoodVision's SmartRouter is an OpenAI-compatible gateway (`/v1/chat/completions`, `/v1/models`, Bearer auth). The routing policy bound to your API key decides which model serves a request when the model id is `auto`; any other id must match your account's model market verbatim.

## Setup

1. Create an API key in the GoodVision console (**SmartRouter settings → Create API key**). The secret is shown once. Keys are environment-specific: a key issued on the test console works only against the test host.
2. In Cline, open Settings → API Configuration and choose **GoodVision SmartRouter**.
3. Paste the key. The **Base URL** defaults to the test host, `https://api-test.goodvision.tech/v1`; set it to `https://api.goodvision.tech/v1` for production.
4. Pick a model. The picker lists your key's live model market (fetched from `/v1/models` with your key). `auto` lets the routing policy choose per request; you can also type any market id.

The provider also reads the `GOODVISION_API_KEY` environment variable when no key is saved.

## Routing and cost

- Routing is decided by the policy bound to the key in the console; the request itself cannot steer it. Each response carries the served model in its `model` field and in the `x-gv-selected-model` header.
- The SmartRouter returns standard OpenAI `usage` (prompt and completion tokens) but no cost. Cline prices requests with a snapshot of list prices for the known market models; the router's usage page in the console is the authoritative bill. Requests on `auto` are not priced because the served model varies.

## Tool calling through the prompt

The SmartRouter matches each request against "model offers" and filters them by capability; a key whose routing policy has no tool-capable offers gets `422 no_candidate` ("No model offer satisfies the effective policy") for any request that declares tools, on every protocol, while the same request without tools succeeds. Whether tools are accepted is therefore a console-side setting, so the GoodVision provider carries `toolTransport: "auto"`: the first tool-bearing request of a session is sent with native `tools`; if the router refuses it with that exact error, the same request is re-sent through the text protocol and the session stays on it (one free round trip; a decision is remembered per session, or for an hour on a handler without a session). In the text protocol, tool definitions are described in the system prompt, the model writes calls as `<tool_call>{"name": …, "arguments": {…}}</tool_call>` blocks, and the provider layer turns those back into native tool calls before the agent loop sees them; tool results travel back as `<tool_result>` text. This is the same text-based protocol the team's ChainSWE harness uses on this key. Once the key's policy allows tools, nothing needs rebuilding: new sessions use native tool calling. The Cline output channel logs the decision as `[goodvision] tool transport: native|prompt`.

It works with every model that follows the format reliably (the Claude and GPT ids in the market do). Should GoodVision enable a tool-capable offer for the key, removing the flag from the provider spec restores native tool calling.

## Current limitations

- The router does not mask upstream failures: if a model is unavailable upstream, requests to it answer 502 `upstream_unavailable` rather than fall back. Cline retries those responses with backoff (five attempts over about a minute, on top of the SDK's own retries), which rides out the router's short blips; a sustained outage still fails the request. Pin a working model id if `auto` keeps routing to one that is down.
- Prompt-based tool calling is a text protocol. The parser forgives the common slips (a code fence around the JSON, a stray closing brace after the arguments, a `json` label before the object). A block it still cannot read is handed to the agent loop as a call with the raw text as input, so the model gets the parse error back as a tool error and usually corrects itself on the next turn; a cut-off object is never completed, since the call would run with partial arguments. There is no provider-side validation of arguments.
