---
title: "GoodVision SmartRouter"
description: "Run Cline through GoodVision's OpenAI-compatible SmartRouter gateway, with policy-driven model routing."
---

GoodVision's SmartRouter is an OpenAI-compatible gateway (`/v1/chat/completions`, `/v1/models`, Bearer auth). The routing policy bound to your API key decides which model serves a request when the model id is `auto`; any other id must match your account's model market verbatim.

## Setup

1. Create an API key in the GoodVision console (**SmartRouter settings → Create API key**). The secret is shown once. Keys are environment-specific: a key issued on the test console works only against the test host.
2. In Cline, open Settings → API Configuration and choose **GoodVision SmartRouter**.
3. Paste the key. The **Base URL** defaults to the test host, `https://api-test.goodvision.tech/v1`; set it to `https://api.goodvision.tech/v1` for production.
4. Pick a model. The picker lists your key's live model market (fetched from `/v1/models` with your key). `auto` lets the routing policy choose per request; you can also type any market id.

The provider also reads the `GOODVISION_API_KEY` environment variable when no key is saved.

## Routing and cost

- Routing is decided by the policy bound to the key in the console; the request itself cannot steer it. Each response carries the served model in its `model` field and in the `x-gv-selected-model` header.
- The SmartRouter returns standard OpenAI `usage` (prompt and completion tokens) but no cost. Cline prices requests with a snapshot of list prices for the known market models; the router's usage page in the console is the authoritative bill. Requests on `auto` are not priced because the served model varies.

## Tool calling through the prompt

Under its default routing policy the SmartRouter refuses any request that declares tools (every model answers `422 no_candidate`), while the same request without tools succeeds. Cline's agent loop needs tools on every request, so the GoodVision provider carries the `toolTransport: "prompt"` flag: tool definitions are moved out of the request and described in the system prompt, the model writes calls as `<tool_call>{"name": …, "arguments": {…}}</tool_call>` blocks, and the provider layer turns those back into native tool calls before the agent loop sees them. Tool results travel back as `<tool_result>` text. This is the same text-based protocol the team's ChainSWE harness uses on this key.

It works with every model that follows the format reliably (the Claude and GPT ids in the market do). Should GoodVision enable a tool-capable offer for the key, removing the flag from the provider spec restores native tool calling.

## Current limitations

- The router does not mask upstream failures: if a model is unavailable upstream, requests to it fail rather than fall back. Pin a working model id if `auto` routes to one that is down.
- Prompt-based tool calling is a text protocol: a model that writes a malformed block gets the parse error back as a tool error and usually corrects itself, but there is no provider-side validation of arguments.
